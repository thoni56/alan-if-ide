= Finding and fixing compiler errors

The compiler tells you what is wrong with your adventure, and the IDE shows you where.
This section is about reading what it says, and getting to it.

== You do not run the compiler

There is no build command and no button to press.
The real Alan compiler runs while you type, and what you see in the editor is its opinion of the adventure as it stands at that keystroke.

The `.alan` file you are working in is compiled from the editor, unsaved text and all.
You don't have to save to see whether what you just wrote compiles.

An imported `.i` file is compiled from the disk, since that is where the compiler reads it.
While such a file has unsaved changes the IDE shows no compiler errors for it at all, rather than errors from a version on disk that no longer matches what you are looking at.
Save the file and its errors appear.

[NOTE]
====
If a `.i` file has stopped reporting errors, look at its tab for the unsaved dot.
That is the most likely reason.
====

== Where the errors appear

An error shows up in three places at once.
Work from whichever suits what you are doing.

*In the text*, as a red underline on the part of the line the compiler objected to.
Hover over it to read the message.

*In the Problems panel* (menu:View[Problems], or kbd:[Ctrl+Shift+M]), as a list grouped by file.
Click an entry and the editor opens that file with the cursor on the error.
Use this one when the adventure spans several files, since it collects the errors from all of them.

*In the status bar*, as a count of errors and warnings.
Click it to open the Problems panel.

== Reading an Alan error

Here is the smallest broken adventure there is, a main file with nothing but a start clause pointing at a location that was never written:

[source,alan]
----
Start At kitchen.
----

The compiler reports:

----
310 E : Identifier 'kitchen' not defined.
----

There are three parts.

`310` is the compiler's own error number.
It is stable between versions, so it is the thing to quote when you ask another author what an error means.
The Problems panel shows it as the diagnostic code `alan.compiler.310`.

`E` is the severity.
`E` is an error, and no adventure is generated.
`W` is a warning: you still get an adventure, but the compiler thinks you probably didn't mean this.
`F` and `S` are a fatal error and an internal compiler error, which you are unlikely to ever see; the IDE shows both as errors.

The rest is the message, written from the compiler's point of view.
Here it is telling you that something referred to `kitchen`, and nothing declares it.
Write the location, or point the start clause at one that exists.

[NOTE]
====
The compiler also has purely informational messages, marked `I`.
The IDE doesn't ask for them, so they never reach the Problems panel.
====

== Errors in a file you are not looking at

An Alan adventure is compiled as a whole, from its main file.
An error in an imported `.i` file is found while compiling the main file, and the IDE puts it where it belongs.
You get the red underline on the offending line of `lib/rooms.i` even though the compiler was run on `game.alan`, and the Problems panel lists it under `lib/rooms.i`.

=== Which file counts as the main file

The rule is mechanical, and it is not the setting you might expect.

When you are editing a `.alan` file, that file is the main file.
It is compiled as itself.

When you are editing a `.i` file, the IDE compiles the first `.alan` file in the same directory, in alphabetical order.
It does not search subdirectories, and it does not look at the folder above.

[IMPORTANT]
====
The `alanif.mainFile` setting does not affect this.
That setting tells *Play* which adventure to run, and nothing else.
====

Two things follow.

If a directory holds more than one `.alan` file, the alphabetically first one is used, silently.
If that is not the one that imports the `.i` you are editing, the errors you see are that other adventure's.

If a `.i` file sits in a directory with no `.alan` file beside it, a `lib/` subfolder say, there is nothing to compile it as part of, and it gets no compiler errors at all.
Nothing is reported to say so.
The file stays quiet, however wrong it is.
Open a `.alan` file that imports it and the errors turn up there, against the imported file.

=== Two files with the same name

Errors are matched to files by filename alone, ignoring the directory.
If your adventure has a `chapter.i` in two different folders both will show the same errors, and one set of them is wrong.
Give such files distinct names.

== When you see no errors at all

An empty Problems panel is good news, as long as the compiler is actually running.
There are a few ways for it to be quiet for the wrong reason.

*No compiler is installed or configured.*
Without the Alan compiler the IDE can't produce compiler errors, and it doesn't invent them.
Syntax errors from the editor's own parser still appear, but undefined names, type errors and everything else the compiler checks go unreported.
Run *Alan IF: Check Setup* from the Command Palette (kbd:[Ctrl+Shift+P]) to see whether a compiler was found, and where.
The language status bubble beside "Alan" in the status bar says the same thing while an Alan file is open, and a `⚠ Alan setup` item appears in the status bar whenever something is missing.

*The `.i` file you are editing has unsaved changes.*
See above, save it.

*The `.i` file has no `.alan` file beside it.*
See above, there is nothing to compile it as part of.

*Something went wrong running the compiler.*
You don't get a dialogue for this.
It goes to the output channel instead: menu:View[Output], then pick *Alan IF Language Server* from the dropdown.
A compiler that could not be started, one that took longer than a minute, or one too old to understand the options the IDE passes it, all report themselves there.

== A practical loop

Write a little.
Watch the underline come and go as you type.
When you have finished a passage, save, which is also what lets any imported file you touched report itself.
Then glance at the Problems panel before you move on.

[TIP]
====
The main file is compiled on every keystroke, so a very large adventure can make typing feel heavy.
If that happens it is the compile you are feeling, not the editor.
====
