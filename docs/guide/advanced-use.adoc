== More than one main file

* Play picks its file as: `alanif.mainFile`; else the active `.alan` file; else the first `.alan` beside the active `.i`; else the first `.alan` anywhere in the folder.

== Sub-directories

// Verified against the extension sources at 34b03b5 and alan 3.0beta9, by compiling
// the way the IDE does: a temp copy of the main file, with the working directory and
// -include both set to the main file's folder.
// The compiler's import lookup may change (alan-if/alan#57), so check these again before writing.

* Imports resolve against the main file's folder, not the importing file's.
`Import 'lib/rooms.i'.` finds `lib/rooms.i`.
`Import 'rooms.i'.` does not, and gives `199 F : Adventure source file (rooms.i) not found.`
* So the standard library does not work from a subfolder.
`library.i` imports its siblings by bare name, and every one of them is `199 F` not found.
There is no include-path setting to change that.
* A backslash in an Import path is not found on Linux.
Windows is untested.
* An error in `lib/rooms.i` still gets its red underline there, and the *Problems* view lists it under `lib/rooms.i`.

* If a `.i` file sits in a directory with no `.alan` file beside it, a `lib/` subfolder say, there is nothing to compile it as part of, and it gets no compiler errors at all.
Nothing is reported to say so.
The file stays quiet, however wrong it is.
Open a `.alan` file that imports it and the errors turn up there, against the imported file.

== Re-Playing

  Replaying a walkthrough is the easiest testing there is. I checked this:
  - Type @walk.a3s at the game's prompt, and arun reads the commands from that file one by
    one. It works in the Play terminal, with no setup.
  - The reader writes the file in the editor, as a plain list of commands.
  - arun -c would write such a file from a session that's actually played, but Play doesn't
    pass switches, so that one is for later or for Advanced use.
